## 二、根因（已量化定位）

DSH 桌面端（Electron）界面比 web 端系统性偏暗。**不是**渲染器、GPU 合成或色彩管理差异，而是**皮肤的一个 CSS 变量被桌面端的布局插件用错了地方**：

1. 皮肤 `src/client/vj815.module.css:102` 定义 `--dsw-specific-sidebar-fill: rgba(14, 16, 12, 0.88)`（88% 不透明深色，语义本应是「侧栏填充」）。
2. 桌面端插件 `@deepseek-ai/dsh-client-ui-layout` 在 **Windows 标题栏模式**下，把**整个框架容器**刷成这个变量（本机桌面端页面内遍历 `document.styleSheets` 取到的原文）：

   ```css
   .BynINW_frame { background: var(--dsw-alias-bg-base); ... }
   [data-windows-titlebar] .BynINW_frame {
     --dsh-windows-content-radius: 16px;
     box-sizing: border-box;
     padding-top: var(--dsh-windows-titlebar-height);
     background: var(--dsw-specific-sidebar-fill);      /* ← 罪魁 */
     grid-template-rows: minmax(0px, 1fr);
   }
   [data-windows-titlebar] .BynINW_frame::before {
     content: ""; height: var(--dsh-windows-titlebar-height);
     background: var(--dsw-specific-sidebar-fill);
     app-region: drag; position: absolute; inset: 0px 0px auto;
   }
   ```

3. `.BynINW_frame` 是铺满视口的顶层容器（属性 `data-dsh-frame`，实测 1920×1032；`data-windows-titlebar` 实测落在 `<html>` 上）→ 一层 88% 不透明的深色盖在 `body` 的油画背景之上。
4. **web 端没有 `data-windows-titlebar`**，同一容器走 `background: var(--dsw-alias-bg-base)`，因此不受影响。这解释了「同一套皮肤，桌面端黑、web 端正常」。

### 量化证据（同视口 1920×1032 / dpr=1 / 首页状态）

| 指标 | 桌面端（修前） | 桌面端（运行时中和该背景后） | web |
|---|---|---|---|
| 整体 Mean | 30.1 | **40.4** | 40.1 |
| 暗像素(<32) 占比 | 91.5% | **63.2%** | 63.0% |
| 右侧纯背景区 (x1500-1900, y200-700) | 24.4 | **31.5** | 31.7 |

排除项（均为两侧逐字节/逐点相同，故不是变量）：

- 纯色探针（#000000 / #202020 / #404040 / #808080 / #c0c0c0 / #ffffff）+ 渐变 `linear-gradient(rgba(10,12,8,.6)→rgba(8,10,6,.9))` 叠 `#808080` → 桌面端与 web 端输出**逐字节相同**（含 `(33,35,32)`）→ 无色彩管理/gamma 偏移。
- 同一张油画（页面 `body` 的 data URI，长度 277151）放普通 div，`background-size:cover` + `50% 42%`，400×400 与全屏 1920×1032 两种尺寸 → 两侧**逐点相同**（平均绝对差 0）。
- `background-attachment` 由 `fixed` 改 `scroll`：30.1 → 30.1，无变化。
- 两侧皮肤产物同版本同哈希（`0.1.36`，`lib/client.js` 1,041,375 B，SHA256 前缀 `85974B98FA056403`）。

## 三、修复补丁

在皮肤里给 Windows 标题栏模式的框架容器覆盖背景（**只影响桌面端；web 端与 40px 顶部标题条不变**，已在本机运行时验证）：

```css
body[data-dsh-815] [data-windows-titlebar] [class*="frame"][data-dsh-frame] { background: transparent; }
```

**落点**：`src/client/index.ts` 的 `appendRule` 段，紧接现有的两条 frame 规则（当前 183-184 行）：

```ts
appendRule('body[data-dsh-815] [class*="frame"][data-wco] { grid-template-rows: env(titlebar-area-height, 40px) 1fr; }')
appendRule('body[data-dsh-815] [class*="frame"][data-desktop] { grid-template-rows: 32px 1fr; }')
// 新增：桌面端把整个框架容器刷成了 --dsw-specific-sidebar-fill（皮肤里是 88% 深色），
// 会盖住 body 上的油画背景；这里只把框架底恢复透明，标题条与三列各自底色不动。
appendRule('body[data-dsh-815] [data-windows-titlebar] [class*="frame"][data-dsh-frame] { background: transparent; }')
```

选择器选 `[data-dsh-frame]` 是为了**只命中布局框架容器**，不要用宽泛的 `[class*="frame"]`（会误伤 `dsh-client-ui-attachment`、`-subagent`、`-sidebar-browser` 等插件的 `.xxx_frame` 类）。

**不要**采用「把 `--dsw-specific-sidebar-fill` 改亮/改透明」的方案：该变量同时用于侧栏与标题条填充，且 web 端也在用（`vj815.module.css:102` 位于 `body[data-dsh-815]` 变量块内），牵动面大。

## 六、环境与坑（本轮实测）

1. **别用 CDP `Emulation.setDeviceMetricsOverride` 造同视口**。桌面端真实窗口若只有 1280×820，override 到 1920×1032 后 `background-attachment: fixed` 的绘制与真实视口错配，会得到假数据。用 `desktop-window.ps1 maximize` 真实最大化（Win32 `ShowWindow(SW_MAXIMIZE)`）。
2. Electron 的 CDP **没有** `Browser.getWindowForTarget`（报 `-32601`），`cdp-window.mjs` 的窗口调整会静默跳过。
3. **探针会绕过叠加层**：`z-index:2147483647` 的探针在页面最上层，它两侧一致**不能**证明整页一致。判断「渲染器有没有差异」用探针，判断「页面上哪一层在压暗」要用 DOM 分层枚举（`dom-layers.js`）+ 逐层中和。
4. 截图统计口径复用 `pixel-stats.ps1`（GetPixel step=4；右侧背景区固定 x1500-1900 / y200-700），`pixel-diff.ps1` 做逐点差异。
5. 桌面端窗口最大化时 `GetWindowRect` 会报 `-8,-8 1936x1048`（Windows 对最大化窗口的边框外扩），内容区仍是 1920×1032，属正常。

本轮脚本都在 `C:\lengduan\githubs\ds-harness\.scratch\desktop-eval\`：`pixel-stats.ps1` / `pixel-diff.ps1` / `desktop-window.ps1` / `cdp.mjs` / `probe.js` / `bgprobe.js` / `bgprobe-full.js` / `dom-layers.js` / `find-frame-css.js` / `hide-overlay.js` / `fix-frame-precise.js` / `clean.js`。诊断全文见同目录 `05-根因-桌面端偏暗.md`（含完整证据链）。
