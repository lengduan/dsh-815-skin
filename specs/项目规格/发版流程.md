# 发版流程

- 状态：生效中（2026-11-06 建立）
- 适用范围：npm 包 `@lengduan/dsh-client-ui-skin-815` 的版本发布，涉及 `.github/workflows/publish.yml`、`package.json`、`CHANGELOG.md`。
- 本文管**发布链路**；视觉与选择器约束见同目录 `皮肤设计风格.md`、`皮肤样式锚点.md`。

## 一、发布方式

- 走 npm 可信发布（Trusted Publishing / OIDC）：workflow 声明 `id-token: write`，`npm publish` 由 npm CLI 用 OIDC 换短期凭据，**不设** `NODE_AUTH_TOKEN`，provenance 自动生成。
- 触发条件是 push 纯版本号 tag，pattern 为 `[0-9]+.[0-9]+.[0-9]+`（无 `v` 前缀）；`workflow_dispatch` 用于手动补发。
- workflow 内有一条硬校验：tag 名必须与 `package.json` 的 `version` 完全一致，不一致直接失败。

## 二、发版步骤

1. 本地预演，在干净副本里跑 CI 会跑的东西，不要在工作区试：

   ```powershell
   git clone --depth 1 <仓库> $env:TEMP\dsh-815-sim
   cd $env:TEMP\dsh-815-sim
   pnpm install --frozen-lockfile
   pnpm build
   pnpm test
   npm pack --dry-run
   ```

   判据：install / build / test 全绿，pack 清单与 `files` 字段一致。

2. 改 `package.json` 的 `version`，并在 `CHANGELOG.md` 顶部加 `## X.Y.Z — YYYY-MM-DD` 条目（格式沿用既有条目：先说修什么，再用要点列证据与做法）。

3. 提交，只含上面两个文件：

   ```
   chore(release): 发布 X.Y.Z
   ```

4. 推主分支：`git pull --rebase origin main` → `git push origin main`。有 pull 冲突就停下来问，不擅自跳过或改冲突文件。

5. 打 tag 并推送：`git tag X.Y.Z` → `git push origin X.Y.Z`。tag 必须打在包含发版提交的 HEAD 上。

6. 观察运行：

   ```powershell
   gh run list --repo lengduan/dsh-815-skin --limit 3
   gh run watch <run-id> --repo lengduan/dsh-815-skin --exit-status
   ```

   发布成功的日志特征是三行（缺任何一行都说明链路不完整）：

   - `Publishing to https://registry.npmjs.org/ with tag latest and public access`
   - `Signed provenance statement with source and build information from GitHub Actions`
   - `Provenance statement published to transparency log: https://search.sigstore.dev/?logIndex=...`

## 三、npm 审核等待（发布成功不等于立即可用）

`npm publish` 步骤返回 success，只表示包已提交到 registry；版本随后进入 npm 的自动审核，状态为 `Validating`。这段时间以 404 和旧 `latest` 表现，**属正常现象，不是发布失败**：

- `npm view <pkg>@<版本> version` → 404 `No match found for version`
- `npm view <pkg> dist-tags.latest` → 仍指向上一版本
- npm 包页面提示 "Automated review hasn't finished. The version will remain unavailable until review completes."

实测记录（0.1.42）：publish 步骤于 2026-11-05T23:45:26Z 完成，`dist-tags.latest` 在 2026-11-06 07:47:16 +08:00（即 23:47:16Z）指向 0.1.42，间隔约 110 秒。等待时长不固定，与包体量、发布时间有关，可能远超本例。

纪律：

1. 审核期间**不要重复发布**——版本号已被占用，重复发布会直接被拒。
2. 不要因为 404 就去改 workflow 或凭据；先等审核结束。
3. 超过一天仍停在 `Validating`，再回头查包设置与 npm 支持，不要在此之前反复重试。

## 四、生效判据

三条同时满足才算这次发布结束：

1. npm 包页面该版本状态为 Published；
2. `dist-tags.latest` 指向新版本；
3. `npm view <pkg>@<版本> repository.url dist.attestations --json` 返回正确的 `repository.url` 与非空 provenance。

## 五、本机环境注意事项

- github.com 与 registry.npmjs.org 直连不通，git / npm / gh 都要走本机代理 `http://127.0.0.1:7897`：
  - git：`git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push ...`（临时覆盖，不改 git config）
  - npm 与 gh：设 `HTTPS_PROXY`、`HTTP_PROXY` 环境变量（npm 不读系统代理）
- 任何 push 前先 `pull --rebase`；push 失败停下来问，不用 force push。
- pnpm 版本与 `pnpm-lock.yaml` 对齐（当前 12.4.1），workflow 里的 `pnpm/action-setup` 固定同一版本。

## 六、常见失败对照

| 症状 | 根因 | 修法 |
|---|---|---|
| `ENEEDAUTH` / 401 | npm 侧 Trusted Publisher 的 Workflow filename 与仓库文件名不一致；缺 `id-token: write`；跑在自托管 runner 上 | 逐项对照 `publish.yml` 文件头的四条前置条件 |
| 推 tag 后没有 run | tag pattern 不匹配（带了 `v` 前缀），或 tag 打在未含 workflow 的提交上 | 改 pattern，或先让 workflow 进默认分支再打 tag |
| 发布被拒：版本已存在 | `package.json` 版本没 bump | bump 后再 tag |
| publish 成功但版本查不到 | 自动审核未完成 | 等待，见第三节 |
| `ERR_PNPM_OUTDATED_LOCKFILE` | lockfile 与 package.json 不同步 | 本地 `pnpm install` 后提交 lockfile |
| provenance 生成失败 | `package.json` 的 `repository.url` 与 GitHub 仓库不一致 | 补齐 `repository` 字段 |
